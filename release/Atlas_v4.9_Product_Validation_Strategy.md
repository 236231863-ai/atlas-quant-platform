# Atlas v4.9 产品验证策略（Product Validation Strategy）

> 阶段性质：真实用户价值验证 Sprint（非功能开发）
> 核心假设验证：**「Atlas 是否能成为购彩者的彩票资产管家」**

---

## 一、产品定位（v4.9 冻结）

> **Atlas = 个人彩票资产管家**：帮购彩者保存每一注彩票、自动核对开奖、管住预算与风险、复盘购彩行为。

**红线（不可触碰）**：
- 禁止号码预测 / 中奖预测 / 提高中奖概率宣传
- 禁止增加无用户验证的功能

**执行原则**：
1. 产品优先于代码
2. 数据优先于猜测
3. 用户行为优先于功能数量
4. 所有新增必须回答："它是否增加用户留存？"

---

## 二、目标用户定义

### 目标用户

| 类型 | 画像 | 核心痛点 | Atlas 承接 |
|------|------|---------|-----------|
| **A：每周购买大乐透/双色球用户** | 每周固定购彩 1-3 次，多注 | 记不清买了啥、总忘记查开奖 | 票据管理 + 自动兑奖 + 提醒 |
| **B：长期购彩但不知道中奖情况用户** | 长期买，但从不/很少对奖 | 中没中不知道，可能错过奖金 | 自动兑奖 + 兑奖通知 |
| **C：希望管理彩票投入的人** | 有预算意识，想知道花了多少 | 花费失控、无复盘 | 资产中心 + 预算 + 行为报告 |

### 非目标用户（明确不做）

| 类型 | 原因 |
|------|------|
| 随机购买一次用户 | 无管理需求，价值为零 |
| 号码预测用户 | 与红线冲突，且非真实需求（数学上不存在） |

**判断**：只服务「有持续购彩行为 + 有管理意愿」的用户，其他用户不承接。

---

## 三、北极星指标

> ## Weekly Active Lottery Users（WALU）
> **每周有真实彩票行为的活跃用户数**（本周内保存≥1张票 或 查看≥1次兑奖结果的用户）

**为什么是这个指标**：
- 同时衡量「建档」（保存）与「回访」（兑奖/报告）——不是"打开就算活跃"，而是"有彩票行为才算"。
- 直接对应留存闭环核心：保存→兑奖→回访。

**定义口径**：
- 活跃 = 本周（周一~周日）内发生 `first_ticket_saved`（后续任意 `ticket_saved`）或 `prize_checked` 或 `draw_reminder_clicked`。
- 单位：用户数 / 周。

**护栏指标**：
| 指标 | 目标 |
|------|------|
| 首次保存彩票完成率 | ≥50% |
| D1 留存 | ≥40% |
| D7 留存 | ≥30% |
| 开奖提醒点击率 | ≥30% |

## 四、验证假设

### 待验证的核心问题
1. 用户为什么第一次安装？→ 获客假设（价值主张测试）
2. 用户为什么第二周回来？→ 留存假设（周留存结构）
3. 用户为什么保存彩票？→ 建档动机（痛点强度）
4. 用户是否愿意付费？→ 付费意愿（premium 兴趣）

### 验证方式
- P1 用户实验系统（埋点事件，CSV 可导出）
- P3 A/B/C 价值主张实验（首次保存率/次日/7日）
- P4 真实数据仪表盘（集中呈现）
- P5 商业兴趣测试（premium_view/click）

---

## 五、v4.9 范围边界

### 做什么
- 建立用户实验系统（事件埋点 + 导出）
- 优化首次 5 分钟流程（30秒价值 / 3分钟建档 / 5分钟资产）
- A/B/C 价值主张实验
- 验证仪表盘 + 商业兴趣测试
- Red Team + CEO 决策

### 不做什么
- ❌ 不加预测/推荐功能
- ❌ 不加新分析模块
- ❌ 不做真实收费（只测兴趣）
- ❌ 不优化非用户路径的复杂功能

---

## 六、成功标准

**v4.9 结束时的判断依据**：
1. 事件系统能真实采集 ≥50 个用户的行为（可导出 CSV）
2. 首次保存完成率、D1/D7 留存数据可见（哪怕样本小）
3. A/B/C 中有一个价值主张显著优于其他
4. CEO 能基于真实数据回答：谁会使用 / 为什么不用微信 / 为什么 7 天后回来 / 为什么愿付 ¥9/月

> 核心目标：**证明「有人真的需要 Atlas」，而非做出功能最多的彩票软件。**
