# Atlas v4.9.1 — Mobile MVP v0.1 详细设计

> 阶段：v4.9.1 P3 · 性质：**详细设计（非开发阶段）**
> 前置：移动端验证策略已通过审核（A）
> 目标：设计一个最低成本验证产品，用真实用户证明「手机端彩票管理需求」
> 禁止：iOS App / 复杂后台 / AI预测 / 号码推荐 / 社区 / 商城 / 扩展桌面功能

---

## 一、Mobile MVP 产品定义

### 1. 用户是谁

| 维度 | 定义 |
|------|------|
| 核心用户 | **每周购买大乐透/双色球的微信用户**（A 类种子用户） |
| 典型画像 | 30-55 岁，在彩票店/体彩 App 买票，会忘查开奖，有微信但不装彩票 App |
| 非目标 | 号码预测爱好者 / 只买一次的人 / 不需要微信的人 |

### 2. 核心痛点

| # | 痛点 | 现有解法为何不够 |
|---|------|----------------|
| P1 | **忘了查开奖** | 微信搜开奖麻烦，官方 App 要安装 |
| P2 | **中了小奖不知道/忘了兑** | 5 元 10 元懒得查，弃奖率高 |
| P3 | **买多了记不清花多少** | 纸票一堆，月底对不上账 |
| P4 | **丢票/撕票后无记录** | 无电子归档 |

### 3. 一句话价值

> **微信里管好每一注彩票：录票自动查奖，中了就提醒，不再漏掉任何一注。**

### 4. 为什么微信小程序优于 APP

| 维度 | 微信小程序 | 独立 APP |
|------|-----------|---------|
| 触达 | 彩票群/好友转发即用，**0 安装** | 需下载 + 安装 + 授权 |
| 注册 | 微信一键授权，**0 注册成本** | 手机号/账号注册 |
| 提醒 | **微信订阅消息**（用户已习惯微信通知） | APNs/厂商推送 |
| 信任 | 微信背书，彩票数据在微信生态内 | 独立品牌需冷启动信任 |
| 成本 | 一套小程序 2-3 周 | iOS+Android 2-3 个月 |
| 更新 | 无需审核即时发版 | App Store 审核 |

> **结论**：验证阶段用户要的是「微信里能提醒 + 查奖」，不是「又一个彩票 App」。小程序恰好命中。**若小程序验证失败，说明手机端服务本身价值弱——更不值得做 APP。**

## 二、用户完整流程

```
首次进入（扫码/群内点开小程序）
   ↓
① 微信授权（获取 openid → 分配 U0001+）
   ↓
② 引导页（3 屏：录票 / 自动查奖 / 开奖提醒）
   ↓
③ 录第一张票（粘贴号码 或 手动输入，大乐透/双色球）
   ↓
④ 保存成功 → 显示「下一期开奖时间 + 已开启提醒」
   ↓
⑤ 开启订阅消息（微信授权提醒）
   ↓
⑥ 开奖日收到订阅消息推送
   ↓
⑦ 点推送打开 → 自动匹配开奖结果 → 显示中奖状态
   ↓
⑧ 未中 → 显示本期未中 + 本月投入统计
    中奖 → 显示奖金 + 兑奖提示（金额/期限）
```

**关键设计**：第 ③④ 步是 MVP 的「Aha 时刻」——**从录票到看到开奖时间 ≤30 秒**。

## 三、MVP 页面设计（最多 6 页）

| # | 页面 | 页面目的 | 用户动作 | 成功指标 |
|---|------|---------|---------|---------|
| 1 | **引导页**（3 屏轮播） | 30 秒理解价值 | 滑动 → 点「开始」 | 引导完成率 ≥80% |
| 2 | **我的票**（首页） | 核心价值展示 | 查看票列表 / 点「+ 录票」 | 首屏加载 <2s |
| 3 | **录票页** | 最低成本录入 | 粘贴号码 / 手动输入 / 选彩种 | **录票完成率 ≥50%** |
| 4 | **开奖结果页** | 中奖状态呈现 | 查看本期匹配结果 | 结果查看率（点击推送后）≥70% |
| 5 | **提醒设置页** | 订阅消息授权 | 开启/管理开奖提醒 | **提醒开启率 ≥50%** |
| 6 | **本月统计页** | 简单资产记录 | 查看投入/中奖/净额 | 统计查看率（周回访）≥30% |

> 6 页之外不设：登录注册页（微信授权即账户）、设置中心（极简内嵌）、客服反馈（内嵌表单）。

## 四、数据架构设计

### 4.1 复用现有埋点体系（不重写）

| 现有能力 | 复用方式 |
|---------|---------|
| **17 事件集** | 小程序页面行为直接映射（见下） |
| **10 里程碑** | `first_open` / `first_ticket_saved` / `first_reminder_enabled` 等沿用 |
| **REAL / SIMULATION 隔离** | `MOBILE` 归入真实统计，`SIMULATION` 禁止进入 |
| **ExperimentTracker** | 作为统计层不变（写入/查询/导出） |
| **UserRegistry（U 编号）** | 小程序授权后分配 U0001+，关联 openid |
| **DailyExperimentLog** | 每日实验记录沿用 |

### 4.2 新增 MOBILE 来源（关键改动点）

**现状**：`events.py:normalize_source()` 将所有非 SIMULATION 值归一化为 `SOURCE_REAL`。

**设计**：
```
① 新增常量：SOURCE_MOBILE = "MOBILE"
② normalize_source() 扩展：
   - "MOBILE" → SOURCE_MOBILE（保持独立来源，不再并入 REAL）
   - 其余非 SIMULATION → SOURCE_REAL（不变，向后兼容）
③ 真实统计口径更新：real_events() 过滤条件
   由 source==SOURCE_REAL 改为 source in (SOURCE_REAL, SOURCE_MOBILE)
   → MOBILE 计入真实统计，但来源可区分（支持移动/桌面分组分析）
④ 漏斗/留存/metrics：同口径（REAL + MOBILE 均为真实）
```

> ⚠️ 需同步修改 `metrics.py` / `funnel.py` / `retention.py` 中「仅 REAL」的过滤逻辑；**现有测试需验证不回归**（P3 测试补 1 条 source 归一化用例）。

### 4.3 事件映射表（小程序 → 17 事件集）

| 小程序行为 | 事件 | 里程碑触发 |
|-----------|------|-----------|
| 首次进入小程序 | `app_install` | first_open |
| 每次打开 | `app_open` | — |
| 完成引导 | `onboarding_start` | first_onboarding |
| 录入一张票 | `ticket_saved` | first_ticket_saved |
| 开启提醒授权 | `reminder_enabled` | first_reminder_enabled |
| 订阅消息下发 | `reminder_sent` | — |
| 点击推送打开 | `draw_reminder_clicked` | first_draw_checked |
| 查看开奖结果 | `draw_checked` | — |
| 查看兑奖结果 | `claim_checked` | first_prize_checked |
| 查看本月统计 | `asset_viewed` | first_asset_viewed |
| 查看付费提示 | `premium_view` | — |

### 4.4 五张核心表

> MVP 最小数据模型，仅支撑验证，不做过度建模。

| 表 | 关键字段 | 说明 |
|----|---------|------|
| **users** | `user_id`(U0001) · `openid`(微信) · `registered_at` · `first_open_at` · `first_ticket_saved_at` · `lottery_type` · `purchase_frequency` · 里程碑字段(reminder_enabled/draw_checked/claim_completed/asset_viewed/weekly_report_viewed) | 对应现有 `registry.py`，追加 `openid` 字段 |
| **tickets** | `ticket_id`(T0001) · `user_id` · `lottery`(dlt/ssq) · `front`(list) · `back`(list) · `cost` · `buy_date` · `draw_date` · `issue` · `claimed` | 对应现有 `TicketManager` 结构，追加 `user_id` |
| **draws** | `issue` · `lottery` · `front` · `back` · `draw_date` | 复用现有开奖数据（内置 1200 期 + 增量更新） |
| **reminders** | `id` · `user_id` · `ticket_id` · `remind_at` · `sent`(bool) · `clicked`(bool) | 订阅消息下发记录（去重 + 点击追踪） |
| **behavior_events** | `event_name` · `user_id` · `source`(MOBILE/REAL) · `timestamp` · `metadata` | 复用 `events.py` 写入 |

**数据关系**：`users 1—N tickets` · `tickets N—1 draws`（按 issue 匹配）· `users 1—N reminders` · `users 1—N behavior_events`

## 五、云端最小架构

### 5.1 现状（已实证）

- `backend/service/user_service.py` = **内存实现**（dataclass + dict，无持久化）
- `backend/api/v1` 有 users/draws/dashboard 路由，但**无真实账号体系 / 无云同步**
- 桌面端票据在本地 `~/.atlas/`

### 5.2 最低成本可行方案（不过度架构）

```
微信小程序（前端）
   ├─ 录票/我的票/开奖结果/本月统计（本地缓存优先）
   ├─ 微信订阅消息（提醒，免后端推送）
   └─ 极简后端 API（仅 4 个接口）
        POST /api/v2/tickets     # 提交一张票
        GET  /api/v2/tickets     # 拉取我的票
        GET  /api/v2/draws/latest# 最新开奖（复用现有 draws 数据）
        POST /api/v2/events      # 埋点上报（复用 events.py）
```

### 5.3 关键决策

| 决策 | 方案 | 理由 |
|------|------|------|
| 存储 | **SQLite 单文件**（或 Supabase 免费层） | 50 用户量级，SQLite 足够；不引入 Postgres 运维 |
| 认证 | **微信 openid 即身份**，不做密码体系 | 最小成本；openid 作 `user_id` 映射键 |
| 提醒 | **微信订阅消息**（一次订阅=一次下发） | 免 APNs/FCM 推送基建；用户习惯微信通知 |
| 埋点 | **POST /events 落到 SQLite**，`source=MOBILE` | 复用 events.py 统计逻辑 |
| 复用 | 开奖数据直接复用现有 1200 期内置 + 增量 | 不重写数据链路 |
| 部署 | 单台云服务器（轻量）+ 小程序后端域名 | 月成本预估 <¥50 |

### 5.4 明确不做

- ❌ 用户密码 / 邮箱注册 / 多设备登录
- ❌ 云端同步桌面票据（跨端一致性）
- ❌ 分布式 / Redis / 消息队列 / 复杂鉴权
- ❌ 真实推送服务（APNs/FCM）——验证阶段微信订阅消息足够

## 七、成功/失败判断

### 7.1 什么数据证明**继续**（成功标准）

| 指标 | 目标 | 证据含义 |
|------|-----:|---------|
| 真实用户数 | ≥50 | 手机端服务有受众 |
| **首次保存率** | ≥50% | 用户愿意录票（价值成立） |
| **提醒开启率** | ≥50% | 用户信任提醒价值 |
| **D7 留存** | ≥30% | 用户一周后回来 |
| **Q2 不便比例** | ≥60% | 用户认为 Atlas 不可替代（微信不能替代） |
| 提醒→打开率 | ≥30% | 提醒是有效召回钩子 |

**全部达标** → 证明「手机端彩票资产管理需求」真实存在 → 进入 APP 战略判断（第八部分）。

### 7.2 什么数据证明**停止**（失败标准）

| 指标 | 触发 | 含义 |
|------|-----:|------|
| 首次保存率 <50% | T+7 | 录票太麻烦 → 定位流程，仍失败则停止 |
| D7 留存 <30% | T+13 | 价值不成立 |
| **Q2 不便 <60%** | T+7 | **微信已够用 → 手机端服务无独立价值 → 停止扩展** |
| 真实用户 <50 | T+14 | 招募失败 / 无受众 |

**任一核心指标未达标** → 停止手机端扩展，回归桌面深耕（保留桌面 + 埋点不动）。

> **失败不是项目死亡**：证明「用户只要微信提醒 + 简单记录，不要独立服务」本身就是有价值的商业结论。

## 八、APP 战略判断（5 问）

> 本部分是**预置判断框架**，最终由验证数据回答（P4 阶段必须用真实数据作答）。

| # | 问题 | 预置判断 | 决定数据 |
|---|------|---------|---------|
| 1 | 小程序数据是否证明需要 APP？ | 小程序达标 ≠ 需要 APP | D7 留存 / Q2 不便 / 主动「想要 APP」反馈 |
| 2 | 用户需要 APP 还是微信提醒？ | **倾向：微信提醒即可**（订阅消息 + 0 安装） | Q2 答案分布（A 怕忘兑奖 vs D 微信即可） |
| 3 | 桌面+小程序是否覆盖需求？ | **大概率覆盖 90%**（录票/提醒/查奖/简单统计） | 用户反馈中「缺 X 功能」是否超 10 条 |
| 4 | APP 增加什么真实价值？ | 深度分析 / 离线 / 品牌 / 推送稳定——但**验证阶段用户未必需要** | 高级功能使用率 |
| 5 | 是否值得投入 2-3 个月？ | **默认否**，除非：D7≥30% + 付费意愿≥20% + 用户明确要求 APP | 付费意愿问卷（Q4） |

**预置结论**：除非小程序验证出现「用户强烈要求 APP」的信号，否则 **MVP 之后的方向是「小程序增强 + 云端账户」，不是原生 APP**。
