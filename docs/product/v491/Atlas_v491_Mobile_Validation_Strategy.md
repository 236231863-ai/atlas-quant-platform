# Atlas v4.9.1 — 移动端验证策略（Mobile Validation Strategy）

> 阶段：v4.9.1 P2 调整 · 性质：**产品验证方案设计**（本阶段不开发、不实现 App）
> 背景：P2 审核结论 **B（需要调整）** —— 从「验证桌面软件」转向「验证用户是否需要手机端彩票资产管理服务」
> 核心立场：**不预设「必须做 APP」**。先用最低成本验证用户真实需要什么形态。
> 约束：不开发桌面功能 / 保留 v4.9.1 埋点体系 / 不删除已有功能 / 只输出方案

---

## 〇、战略第一问：为什么一定要做 APP？

> 这是本策略的**第一性审视**。在写任何方案前，先诚实回答。

**当前存在的真实风险（审核已指出）：**
很多彩票用户可能**根本不需要独立 APP**。他们可能只需要：
- 微信提醒
- 自动查奖
- 简单记录

如果这是真相，那么「做一款彩票 APP」就是**错误的投入方向**。

**可能的真相：**Atlas 的未来形态不是「彩票 APP」，而是**「彩票资产服务平台」**，可能是以下组合：

```
微信小程序（触达 + 轻记录 + 提醒）
   ＋
手机 APP（深度资产管理）
   ＋
桌面专业版（数据分析 / 深度用户）
   ＋
云端账户（跨端同步）
```

**本策略的使命：**不争论「APP 该不该做」，而是用 **14 天、50 名真实用户、最低成本**验证三个事实：
1. 用户是否需要「手机端」彩票服务（还是微信已够用）？
2. 用户最需要的手机能力是什么（提醒 / 查奖 / 记录）？
3. 用户对「独立 APP」 vs 「微信小程序」的真实偏好？

> **结论先行**：验证阶段**不做 APP**，用**微信小程序**（触达成本最低）验证价值；验证通过后再决定是否升级 APP。

## 一、手机端用户场景分析

### 场景清单（按痛点强度排序）

| # | 场景 | 发生频率 | 痛点强度 | 手机端必要性 | 桌面能否替代 |
|---|------|---------|---------|:---:|:---:|
| S1 | 彩票店刚买完，想马上记下号码避免丢票 | 高（每次购买） | ★★★★★ | **必要** | ❌ 人在店外 |
| S2 | 收到开奖推送，想立刻看这期中了没 | 高（每周 3-6 次） | ★★★★☆ | **必要** | ❌ 通知即时性 |
| S3 | 出门在外查历史某注中了多少 | 中 | ★★★☆☆ | 必要 | ⚠️ 可延迟 |
| S4 | 月底看这个月花了多少、中了多少 | 中（月度） | ★★★☆☆ | 方便 | ✅ 可替代 |
| S5 | 中了小奖忘了兑，需要提醒 | 中 | ★★★★☆ | **必要** | ⚠️ 桌面提醒受限 |
| S6 | 帮家里老人管理购彩记录 | 低 | ★★★☆☆ | 方便 | ❌ 老人不用桌面 |

**结论：**
- **S1/S2/S5 是手机端核心价值**——「人在购彩现场 / 开奖瞬间」是手机端不可替代的场景
- 这三类场景的共同点：**轻量、即时、低操作成本** → 天然适合**微信小程序**（0 安装、订阅消息推送），而非重 APP
- 桌面端的「深度分析 / 资产管理」是**加分项**，不是手机端验证的前提

## 二、微信小程序 / Web / iOS 三方案比较

### 评分表（1-5 分，5 最优）

| 维度 | 微信小程序 | 手机 Web/PWA | 独立 iOS APP |
|------|:---:|:---:|:---:|
| **触达成本**（用户获取） | **5**（微信生态内转发） | 3 | 1（需下载安装） |
| **注册门槛** | **5**（微信一键授权） | 3 | 1（需账号注册） |
| **推送能力** | **4**（微信订阅消息） | 2（PWA 推送弱） | **5**（APNs） |
| **开发成本** | **4**（小程序框架，复用后端） | 4 | 1（原生/跨端成本高） |
| **上线速度** | **5**（审核快） | **5** | 2（App Store 审核） |
| **用户信任** | **4**（微信背书） | 3 | 3 |
| **数据同步** | 3（需云 API） | 3 | 3 |
| **商业化能力** | 4（微信支付） | 3 | **5**（内购/订阅成熟） |
| **验证速度** | **5** | 4 | 1 |
| **与现有 Atlas 复用** | 4（复用后端数据逻辑） | 4 | 2 |
| **合计** | **43** | 34 | 24 |

### 结论

| 阶段 | 方案 | 理由 |
|------|------|------|
| **验证阶段（现在）** | **微信小程序** | 触达成本最低、订阅消息推送可用、0 安装门槛、上线最快 |
| 验证通过后增强 | Web/PWA | 跨端补充（非微信用户 / 收藏到桌面） |
| 留存 + 付费验证后 | 独立 iOS APP | 深度用户、支付能力、推送稳定性、品牌 |

> **关键判断**：如果用户连微信小程序都不愿意用，说明「手机端服务」本身价值不成立——更没必要做 APP。**小程序是验证的漏斗第一层。**

## 三、最低成本 MVP 方案

### MVP 范围（必须最小，只做 3 件事）

| 功能 | 说明 | 解决场景 |
|------|------|---------|
| ① 录号码 | 粘贴/手动输入大乐透/双色球号码 | S1 |
| ② 自动查奖 | 录入后自动匹配最近开奖，推送结果 | S2/S5 |
| ③ 简单记录 | 本月投入/中奖/净额（一行数字） | S4 |

### 明确不做（验证阶段禁止）

- ❌ 资产分析 / 行为分析 / 健康分 / 策略复盘（桌面已有，不搬到手机）
- ❌ 号码推荐 / 预测 / 走势图（红线）
- ❌ 用户账号体系 / 云同步（验证价值后再做）
- ❌ 桌面同步 / 多端数据打通

### MVP 技术形态（最小实现）

```
微信小程序（原生小程序框架）
   ├─ 页面：录票 / 我的票 / 开奖结果 / 本月统计
   ├─ 提醒：微信订阅消息（开奖前 + 开奖后）
   └─ 后端：极简 API
        ├─ 复用：开奖数据（现有 draws API / IncrementalUpdater 逻辑）
        └─ 新增：tickets 存录（本地 or 极简云存储）
```

**预估工作量**：1 名开发 2-3 周（含审核 + 50 人内测）

> ⚠️ **现有后端不能直接复用做云同步**：`backend/service/user_service.py` 是内存级实现（无持久化），`backend/api/v1` 无真实账号体系。MVP 只需要「存 50 人的票 + 查开奖」，用极简方案（小程序本地缓存 or 单表云存储）即可，**不需要先建完整账号体系**。

## 四、50 人真实测试方案

### 招募（沿用 v4.9.1 渠道与红线）

| 渠道 | 说明 |
|------|------|
| 微信好友 + 彩票交流群 | 精准 A 类用户（每周购彩者） |
| 首批 ≥10 人 | T+1 门槛 |

**红线**：模拟用户 / 自动生成 / 压测数据 ❌

### 用户流程（30 秒价值）

```
扫码进入小程序
  → 微信一键授权（自动分配 U0001+，关联微信 openid）
  → 引导：录 1 张最近买的票（粘贴号码）
  → 一键开启「开奖提醒」
  → 看到：我的票 / 下期开奖时间
  → 开奖后自动推送：中了没 / 中多少
```

### 用户编号（沿用 P1 体系）

- `UserRegistry.register()` 分配 U0001-U0050
- 新增关联字段：`mobile_openid`（微信唯一标识，用于推送与去重）
- **不破坏**现有桌面用户编号体系

### 每日记录（沿用 P1 daily_log）

- 产品负责人每日登记：新增用户 / 首次打开 / 保存票 / 开启提醒 / 开奖查看 / 反馈
- 存储与导出沿用 `daily_log_v491.jsonl`

## 五、事件埋点如何复用现有 analytics

### 核心原则：**一套事件集，两种来源**

现有 `engine/user_experiment/events.py` 已具备 **17 事件 + 10 里程碑 + REAL/SIM 隔离**，验证阶段**不新建事件体系**，仅：

1. **新增来源标记**：`source` 增加 `MOBILE`（与现有 `REAL` / `SIMULATION` 并列）
   - 桌面真实用户 → `REAL`（不变）
   - 小程序真实用户 → `MOBILE`（新增，归入真实统计）
   - 模拟数据 → `SIMULATION`（禁止进入真实报告）

2. **事件映射**（小程序页面行为 → 现有事件集）：

| 小程序行为 | 映射事件 | 说明 |
|-----------|---------|------|
| 首次进入小程序 | `app_install` | 小程序首次授权 |
| 打开小程序 | `app_open` | 每次会话 |
| 完成引导 | `onboarding_start` | 复用 |
| 录入一张票 | `ticket_saved` | 复用 |
| 开启开奖提醒 | `reminder_enabled` | 复用 |
| 收到订阅消息推送 | `reminder_sent` | 复用 |
| 点击推送打开 | `draw_reminder_clicked` | 复用 |
| 查看开奖结果 | `draw_checked` | 复用 |
| 查看兑奖结果 | `claim_checked` | 复用 |
| 查看本月统计 | `asset_viewed` | 复用 |
| 查看周报 | `weekly_report_viewed` | 复用 |
| 看到付费提示 | `premium_view` | 复用 |

3. **统计层不变**：`ExperimentTracker` / `funnel` / `retention` / `metrics` 直接复用，只需在过滤时把 `MOBILE` 并入真实统计

> **不重写埋点**，只是给同一事件集增加一个渠道来源。桌面埋点完全不受影响。

## 六、14 天验证指标

### 核心指标（任务书指定）

| # | 指标 | 公式 | 目标 |
|---|------|------|-----:|
| 1 | **访问/安装** | 小程序 UV（首次授权数） | ≥50 人 |
| 2 | **首次保存彩票率** | `ticket_saved / first_open` | **≥50%** |
| 3 | **提醒开启率** | `reminder_enabled / first_open` | 记录（≥50% 为佳） |
| 4 | **开奖查看率** | `draw_checked / 已开奖票数` | 记录 |
| 5 | **D7 留存** | 第 7 天活跃 / 首日用户 | **≥30%** |
| 6 | **不可替代性 Q2** | 问卷「Atlas 消失会不便吗」选 A/B/C 比例 | **≥60%** |

### 辅助指标

- 漏斗：`install → first_open → ticket_saved → reminder_enabled → draw_checked → weekly_return`
- 提醒点击率：`draw_reminder_clicked / reminder_sent`（目标 ≥30%）
- 付费意愿：`premium_click / premium_view`（仅记录，不收费）

### 护栏（fail-fast）

| 护栏 | 触发动作 |
|------|---------|
| 首次保存率 <50% | 标记 B（录票流程太麻烦？） |
| D7 留存 <30% | 标记 B（价值不成立？） |
| Q2 不便比例 <60% | **停止扩展**（微信已够用 = 手机端服务无独立价值） |
| 用户数 <50 | 延长采集 / 扩大招募 |

## 七、验证成功后 → iOS App 路线图

**先明确：验证成功 ≠ 立即做 APP。** 成功标准 = 首次保存率≥50% + D7≥30% + Q2 不便≥60%。之后分四步：

```
阶段1（v5.0）：云端账户 + 票据同步
   └─ 小程序数据上云（用户注册/登录、票据 CRUD）
阶段2（v5.1）：小程序增强
   └─ 家庭管理 / 历史归档 / 月度报告（仅保留高价值项）
阶段3（v5.2）：iOS 可行性复审
   └─ 若留存 + 付费意愿均达标 → 立项原生 iOS（2-3 月）
   └─ 若留存达标但付费弱 → 维持小程序 + PWA（不做原生）
阶段4（v6.0）：原生 iOS 或 PWA 深化
   └─ 依据阶段 3 决策
```

**iOS 原生立项的硬性门槛**（缺一不可）：
- 小程序验证 D7 留存 ≥30%（连续 14 天）
- 付费意愿问卷「愿付 ≥6 元/月」≥20%
- 用户主动反馈「功能不够 / 想用 APP」≥10 条

## 八、验证失败 → 停止扩展的判断标准

### 停止标准（任一触发即停止）

| # | 标准 | 触发动作 |
|---|------|---------|
| 1 | 首次保存率 <50%（T+7 检查） | 停止手机端开发，回到桌面深耕 |
| 2 | D7 留存 <30% | 同上 |
| 3 | **Q2 不便比例 <60%** | **停止扩展**：用户用微信即可 → 手机端服务无独立价值 |
| 4 | 14 天真实用户 <50 | 延长 7 天或终止实验 |

### 停止后的动作（不是项目死亡，是方向修正）

```
停止手机端扩展
   ↓
保留：桌面专业版（已有功能不动）
   ↓
重新定位：Atlas = 桌面级彩票资产管理工具（深耕现有用户）
   ↓
决策点：桌面留存是否值得继续 → 决定 v5.0 走向
```

### 关键认知

- **「验证失败」也是成功的产品结论**——证明「用户不需要手机端服务」比盲目做 APP 值钱得多
- 失败场景下，**微信小程序 + 自动查奖** 本身可能就是用户要的「全部」，Atlas 只需提供桌面增值，无需独立 App

## 附：下一阶段 NEWMAX AI 必须回答的战略问题

> **「为什么一定要做 APP？」**

本策略的答案倾向：**验证阶段不做 APP，先做微信小程序**。但下一阶段必须由 NEWMAX AI 基于真实验证数据（而非推测）回答：

1. 50 名用户中小程序使用数据证明手机端价值了吗？
2. 用户要的是「独立 APP」还是「微信内提醒 + 查奖」？
3. 桌面版 + 小程序组合是否已覆盖用户全部场景？还缺什么？
4. 做 APP 的真实理由是什么（留存 / 付费 / 品牌 / 推送 / 用户要求）——是否经得起数据检验？
5. 如果小程序已满足 90% 需求，做 APP 的边际价值是否值得 2-3 个月投入？

**只有用数据回答这 5 问后，才能决定是否进入 iOS App 路线图。**
