## 二、设计核心（8 部分）

| 部分 | 结论 |
|------|------|
| 一 产品定义 | 每周购彩微信用户 · 痛点=忘查奖/漏兑/记不清 · 一句话=微信里管好每一注彩票 · **小程序优于 APP**（0安装+订阅消息+微信信任） |
| 二 用户流程 | 授权→引导→录票→开提醒→推送→查结果→中奖状态，**录票到看开奖时间 ≤30 秒** |
| 三 页面设计 | 6 页：引导/我的票/录票/开奖结果/提醒设置/本月统计，每页含目的/动作/成功指标 |
| 四 数据架构 | 复用 17 事件+10 里程碑+REAL/SIM 隔离；新增 `SOURCE_MOBILE`；5 张表（users/tickets/draws/reminders/behavior_events） |
| 五 云端最小架构 | 小程序 + 极简后端（4 接口）+ SQLite + 微信订阅消息；**不做密码/云同步/推送基建** |
| 六 实验方案 | 50-100 人 14 天，T+1/T+3/T+5/T+7/T+13 节点，每日沿用 daily_log |
| 七 成败判断 | 成功=保存率≥50%+D7≥30%+Q2≥60%；失败=Q2<60% 或 D7<30% → 停止扩展 |
| 八 APP 战略 | **默认不投入 APP**，除非 D7≥30%+付费意愿≥20%+用户明确要求 |

## 三、关键设计决策（需审核确认）

1. **MOBILE 来源需改 `normalize_source()`**：当前所有非 SIMULATION → REAL；设计改为 `MOBILE` 独立来源但计入真实统计（`real_events` 含 REAL+MOBILE）。**这是唯一需要动现有埋点代码的点**，实现阶段需补测试验证不回归。
2. **微信订阅消息替代推送服务**：验证阶段不建 APNs/FCM，用微信原生订阅消息（一次订阅=一次下发）。
3. **SQLite 单文件**替代 Postgres：50 用户量级足够，月成本 <¥50。
4. **APP 战略默认「不做」**：除非真实数据出现强烈信号。
